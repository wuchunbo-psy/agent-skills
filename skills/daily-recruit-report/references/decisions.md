# 决策记录（规则为什么是这样）

> 维护者参考，不是执行路径。Agent 日常执行只看 SKILL.md。本文件记录每条规则背后的设计约束，供修改/审查时理解决策依据。
>
> 仅记结论性约束（什么/为什么不），不含时间戳、案例叙事。历史沿革见 CHANGELOG。

## 消息意图判读：不用关键词，交给 LLM

意图判读是语义判断（上下文相关），交主会话 LLM 做，禁止关键词匹配。
- 反例佐证约束成立："安排不太合适"含"安排"但是反对；"需要hr帮忙面一轮"无邀约词但是真邀约。字符串匹配在语义场景必然失效。

## raw_messages 不截断

群消息/私聊原文全量导出，不按长度截断。含多个候选人的长消息被腰斩后拆句判读失效。

## 作战清单的设计依据（根本推导）

清单要解决的根本问题：HR 一天的注意力是稀缺资源，清单的唯一价值 = 帮用户把注意力分配到"能最大化推动入职、最小化候选人流失"的动作上。计量单位是动作不是数据。由此推出全部结构约束：

| 根本事实 | 推出的要求 | 落点 |
|---|---|---|
| 注意力有限 → 必须分级 | 全局红/橙/黄分级，不平等铺 | 全局 |
| 候选人不进则退 | 盯"下一步动作 + 保温"伴随 | 模块二 |
| 面试/offer 有时间刚性（错过=事故） | "今日时效"置顶带时间线 | 模块一 |
| 异常是事故源头 | 独立显性化，不埋列表 | 1C |
| 岗位有冷热 | 指导剩余精力投向 | 模块三 |
| 决策不落地=心智负担 | 用户确认后落盘 decisions | 全流程 |
| HR 按工作室/岗位运营，不按阶段 | 模块二按工作室→岗位组织 | 模块二 |
| 决策需上下文（面评+意见） | 每行带面评列+意见列 | 模块二 |
| 岗位健康度看分布 | 3A 岗位×阶段计数矩阵（单元格放人名） | 模块三 |
| 前瞻防事故（撞档/档期） | 1D 未来面试+撞档预警 | 1D |

结构性演进约束（为什么从 v2 改到 v3+）：v2 按阶段分层把同一工作室的人拆到三处，违反"工作室是 HR 真实运营单元"；v2 只给"下一步"不给"上一轮评价"，决策缺上下文。格式子规则的演进史见 CHANGELOG。

## 1B 拆「首次邀约 / 流程推进」的依据

两类动作的执行成本和沟通对象完全不同：首次邀约=录ATS+首次触达候选人+双向约时间（重）；流程推进=只排下一轮面试官档期、offer线走审批（轻）。混排会让用户误判一天的动作量级。判据：「不面了，安排其他人面」「约下对比下」类措辞=候选人已有接触历史，归流程推进。

## 1A 轮次进度链与重点行标注的依据

同一天里第 1 轮和第 3 轮面试的「过了之后」动作完全不同（排下一轮 vs 走 offer），裸轮次文字看不出轻重，要回模块二交叉查。进度链让每场的重要性自包含；符号沿用模块二结论列已有的✅家族、今天的场次用文字（今天）标注——**不发明新图标**：新图标体系要么视觉噪音大（彩色大 emoji），要么要先学图例（抽象圆点链），复用读者已认识的符号零学习成本。1D 前瞻同链但不带（今天）标记：本周哪几场是复试以上的关键场，前瞻时就该可见。重点行加粗+候选人名前⭐用行内标注而非物理分组——时间线必须保持时序才能按小时安排一天，分层靠视觉跳读实现，不靠重排；标记用⭐这类通用记号，不用🎯这类科技感/营销感图标。

## 1B 流程推进按工作室分表的依据

HR 按工作室运营（与模块二同一组织逻辑）。流程推进混在一张大表时跨工作室的人挤在一起，数人数、对岗位、分配今天的沟通对象都要逐行扫。每工作室一张表解决堆积；组内保留岗位列保留团队归属；不做每岗位一张小表——人少时表格碎片化反而稀释重点。

## 空档一览只留日期与排期的依据

空档表的价值是「哪几天有空」这个日历事实。利用建议必然携带条件说明和历史背景（谁哪天不可约、之前问过什么），堆进格子造成信息过载，且塞人的动作信息与 1B/模块二重复。事实归空档表，动作归动作清单。

## 自检清单允许与规则正文并存的原因

自检是输出前的验证闸门（防"知道规则但输出时滑走"），规则正文是执行时的指引——两者职责不同不算冗余。约束：自检每条只写一行检查点+不合格特征，不重述规则全文；规则的完整定义只在输出模板节存在一处。

## 接棒保温必须强制（step 6）

作战清单（今天处理谁）和保温清单（今天碰谁）是同一个早晨决策流的两半。作战清单输出、用户确认决策后，Agent 必须主动继续执行 candidate-nurture，不需用户重新喊"保温"。
- 约束：两个 skill 串行耦合时，"接棒"必须是硬指令而非软建议，否则后半场永远不被触发。

## _my_jobs.json 是会过期的快照

对账脚本按 `_my_jobs.json`（我创建的岗位 job_id 快照）过滤投递。新创建的岗位不在快照里 → 该岗投递被过滤 → 候选人漏报。
- 约束：岗位增减后必须跑 `refresh_my_jobs.py` 刷新（page_size≤20 全量翻页，>20 返回空）。任何"快照缓存"都不能当真相源。
