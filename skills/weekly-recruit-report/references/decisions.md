# 决策记录（规则为什么是这样）

> 维护者参考，不是执行路径。Agent 日常执行只看 SKILL.md。本文件记录每条规则背后的设计约束，供修改/审查时理解决策依据。仅记结论性约束，不含时间戳、案例叙事。

---

## 四问框架的推导依据

四问不是发明，是 mentor 多轮周报反馈的收敛结构：

| 反馈 | 收敛到 |
|---|---|
| "计划遵循 SMART" | 问④ 可执行（动作+数字+时限） |
| "每周重复条目要写进展+结果+数字" | 问① 结果化 |
| "卡点写清楚，周报是沟通途径，能整合资源" | 问② 卡点显性化 + 写"需要什么" |
| "要结果，不要只说过程" | 问① 的硬要求（完成态而非动作描述） |
| "不要问一句答一句，表达结论先行" | 输出顺序：结果在前，过程细节其次 |

**"为什么会出现"单独成问的原因**：卡点只写现象，读者必然追问原因；先自己归因并把归因落到**可改变层面**（筛选标准/寻访渠道/工作方法/外部依赖），调整动作才有落点。归到"忙/没注意"不可改变，等于只表态不解决。

## 上周计划销账是硬要求

计划-兑现闭环是周报的信用机制：每条计划下周必须以"兑现 / 延期+原因 / 取消+原因"回写。不销账的计划会退化为愿望清单，且读者（mentor）无法区分"没做"和"做了没写"。

## 场次口径必须拆解的约束

周报写"37 场"被质疑偏高，核实结论：**数据真实，表述失真**。偏差来自三处——同人多轮各算一场（12 场来自 6 人的第 2~4 轮）、改期在系统留两条排期（1 场未实际进行）、集中排期使单日密度极高（体感远低于系统数）。由此推出：

- 凡"场"类计量，同时给 排期数 / 实际执行数 / 去重人数 三个口径，初试复试拆开；
- 数字被质疑时先出逐日逐场清单核对事实，再修表述——顺序不能反，先改数字会掩盖口径问题。

## 数据过滤的归属约束

- interviews/applications 接口返回**全系统**数据：个人产出必须双重过滤（creator=本人 + 岗位归属=本人岗位快照）。只过 creator 不过岗位，会把代建排期算进个人产出；只过岗位不过 creator，会把别人线上的量算进来。
- `_my_jobs.json` 是快照会过期（与 daily-recruit-report 同一约束），岗位增减后刷新，否则新岗投递被静默过滤。
- 入职的 stage enter_time 是 HR 操作时间（常为到岗前一晚批量操作），实际入职日以沟通确认为准——两者差一天，写错会被当事人指出。

## 与日报/看板的边界

日报 = 当日行动（作战清单，短期）；看板 = 全局管道管理视图（长期）；周报 = 复盘 + 向上沟通（周节奏）。三者共享同一条 ATS 事实源和对账链路，但读者与产出形态不同，互不替代——正如日报不替代看板，周报也不替代日报。

## md 与 docx 双产物的原因

md 详实版是底稿（数据可追溯、可继续迭代），docx 提交版随团队惯例裁剪（结构固定、篇幅收敛）。两者数字必须一致——docx 里的每个数字都要能在 md 底稿找到出处。
